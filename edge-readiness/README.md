# Edge Deployment Readiness Kit

A small Python CLI for making a release handoff decision at a site that can’t pull from a public registry. It checks the target architecture and required staged files against an approved manifest. After deployment, it can separately check a local HTTP endpoint and emit the result in the same JSON report.

**Start here:** [Passing staging report](reports/staged.json) · [Blocked staging report](reports/blocked.json) · [Source](readiness.py) · [Tests](test_readiness.py) · [Portfolio case study](https://grizzlyse.com/portfolio/#edge-readiness)

## The handoff decision

The release needs two files, modeled on the [K3s/Zarf workload demo](../k3s-airgap-gitops-platform/): a workload package and a matching init package. Both files are present in the broken example, but the workload package is the wrong revision. The CLI catches the checksum mismatch, tells the operator to restage it, and exits nonzero. Restaging the approved fixture clears that gate. A passing staging report does **not** say an app was deployed.

| Report status | What it means | CLI exit |
| --- | --- | --- |
| `STAGING_PASSED` | Target architecture and every listed file passed. No HTTP check was requested. | `0` |
| `HEALTH_CHECK_PASSED` | Staging passed and the supplied loopback endpoint returned HTTP 200. | `0` |
| `BLOCKED` | A check failed. Inspect the report before proceeding. If staging failed, any requested probe was skipped. | `1` |
| CLI error | The manifest couldn’t be read, is malformed, or the invocation is invalid. | `2` |

## Reproduce the examples

Requires Python 3.11+; no third-party packages. From this directory:

```sh
python3 readiness.py fixtures/release.json fixtures/broken --target-arch amd64
python3 readiness.py fixtures/release.json fixtures/staged --target-arch amd64
python3 -B -m unittest -v
```

The `.fixture` files are text stand-ins, not Zarf archives. The checked-in JSON reports were generated by these CLI invocations. Tests also exercise HTTP 200/503 against an ephemeral loopback server; they do not start K3s.

## Use it with a real lab release

1. On the connected build system, create the real workload package and obtain the matching Zarf init archive. Write a manifest using the real filenames, target architecture, and each file’s SHA-256 from the approved build. Carry the manifest through a trusted channel; don’t regenerate it on the destination after a mismatch.
2. Run `python3 readiness.py release.json ./staged` on the target to use its detected architecture. If checking from a separate machine, give `--target-arch` explicitly; the tool won’t discover the remote node or inspect archive contents to infer their architecture.
3. If staging passes, deploy separately using the [Zarf runbook](../k3s-airgap-gitops-platform/#run-the-offline-workload-demo). Confirm rollout readiness and the image registry as described in the [validation notes](../k3s-airgap-gitops-platform/validation.md). With the app port-forwarded locally, rerun the kit with `--health-url http://127.0.0.1:8080/` and save the JSON to the handoff record.

A release manifest has a human-readable `release`, the expected `architecture` (`amd64` or `arm64`), and an `artifacts` list. Each entry has a relative `path` and a 64-digit `sha256` digest from the trusted build. Use `sha256sum` on the approved archives while staging; the [fixture manifest](fixtures/release.json) shows the exact shape. To retain the report and inspect the exit status, run `python3 readiness.py release.json ./staged > handoff.json` and immediately capture `status=$?` in a shell without `set -e`.

The CLI does not deploy anything, verify signatures, test WAN isolation, or prove that a loopback endpoint belongs to Kubernetes. The HTTP check is a narrow smoke test, not an operational readiness guarantee.
